# Recurring Risks

- Mock tests do not cover provider payload limits, legacy markdown parsing, callback size limits, or SDK lifecycle behavior. Changes touching those areas need protocol or real-device validation.
- Telegram card text is clamped to the 4096 UTF-16 code-unit limit since 2026-08-20 (`clampTelegramText` in `src/inbound/telegram-bot.mjs`, P1-1), with focused protocol-shape tests. The clamp's real-device behavior at the boundary (including proxy escaping differences) still needs one real-device confirmation; other card providers (feishu/qq/wxpusher/dingtalk JSON cards) have no evidence of overflow and stay unclamped until evidence appears.
- Real-device handoff list (2026-08-26, cannot be closed on this Windows host): (1) confirm Telegram clamp boundary; (2) observe Feishu WS / QQ gateway / DingTalk stream reconnects after network blips and suspend/resume; (3) provider payload limits and callback shapes; (4) BurntToast/PowerShell host validation; (5) npm 0.8.6 registry acceptance; (6) QQ gateway RESUME/ACK behavior; (7) QQ C2C, WeChat iLink, and DingTalk image payloads and file/media paths. Current code is wired and contract-tested for image envelopes, but protocol/device evidence is absent.
- Optional inbound dependencies are lazy-loaded; a missing package must produce a visible diagnostic and leave unrelated channels alive.
- Windows desktop toast cannot run in the headless CI matrix; keep `desktop` validation local when touching that adapter.
- `state.json` is shared by the running host and CLI tools. Direct manual edits or bypassing store setters can reintroduce lost updates and stale route reads.
- Version drift can happen through stale `file:` installs or hand-copied `node_modules/dsh-notifier`; use registry installation for acceptance.
- The current release artifact has a known non-runtime `CHANGELOG.md` difference from the engineering archive; resolve or document it before publishing.
- Historical handoff/test-note documents can retain old versions, commit ids, package counts, or green-test claims; treat documentation drift as an operational defect and reconcile it before delegating work.
- Same-process DSH plugins are trusted code, not an isolation boundary. `ctx.emit`, `ctx.provide`, Cordis fibers/isolate, session permission presets, and `node:vm` dynamic-host wrappers do not protect notifier credentials or event content; see `docs/security/PLUGIN_ATTACK_REVIEW.md` and the official Harness architecture evidence recorded there.
- A1/A2 fixed the public notifier event disclosure and directed-send audit gap on `codex/plugin-security-hardening`: cross-plugin events are metadata-only and directed sends share the internal audit callback. Remaining A3-A6 work is tracked in `docs/security/PLUGIN_SECURITY_FIX_PLAN.md`.
- The guided bootstrap pairing code is delivered as a `0600` file (`<stateDir>/bootstrap-paircode.txt`) since 2026-08-23 (batch B-1); logs carry only the path. File permissions are the only barrier, so a same-uid or root process on the host can still read it — the same trust boundary as `state.json` holding scan credentials. The stronger fix (two-factor binding) is deferred to v0.9. No real-device run has yet confirmed the file-delivery flow end to end (boot a real guided instance, `cat` the file, `/pair` from a phone); it is on the real-device handoff list.
- Bounded in-memory learning tables landed 2026-08-24 (batch B-k4 / P1-7, `src/inbound/_bounded.mjs`): dingtalk `sessionWebhooks`/`chatSenders`/`seenMsgIds` and qq `targetKinds`/`msgSeqs` cap at 1024 with LRU touch; `wechat:ctx:` caps at 256 uids in first-seen order; `createTrailingDebounce`/`createGraceQueue` cap at 256 in-flight keys and fire the oldest early instead of dropping it. All evidence is mock fetch/WebSocket plus temporary `state.json`. Real-device gaps: dedup + throttled-warn behavior when a dingtalk group pushes more than 1024 messages inside the 60s window; qq interface selection after eviction with more than 1024 live targets; the real length/charset distribution of iLink `context_token` (the 512-char reject could in principle be tight); and the user-visible effect of an early debounce/grace push.
- `wechat:ctx:` eviction follows first-seen order, not LRU: a long-lived uid that keeps refreshing its token is still evicted before newer uids, because `store` key order does not change on update. Accepted for now (ctx is a cache with a working fallback), pinned by test, and recorded as a residual gap in the handoff tech-debt ledger.
- Button source-chat comparison became fail-closed on the click side on 2026-08-24 (batch C1 / P1-4, `src/inbound/telegram-bot.mjs` ref branch and `src/inbound/feishu-bot.mjs` `sourceChatAllowed`): with origin metadata present, a callback whose own chat id is unreadable is now rejected rather than allowed. All evidence is mock fetch plus a fake Feishu SDK. Real-device gaps: the actual Telegram `callback_query` shape after the card message is deleted (does `message` really go missing?), and whether every real Feishu long-connection card payload carries `context.open_chat_id` — if some card type omits it, the tightening would reject genuine clicks, which is the primary rollback trigger for this change. The legacy allow half (no `origin.chatId`, empty `srcChat`) is deliberately still open per PLAN §C1(b) and is pinned by tests so it cannot be flipped silently.
- WeChat iLink batch 4 provider slice is now wired through `src/channels/wechat-ilink/` with account-scoped cursor/context state, bounded polling, QR-expiry status, and text fallback. The backend protocol remains undocumented/changeable: QR/text/reconnect paths are `contract-tested`; media receive/send is only `declared` behind an optional bridge and has no real-device evidence. Do not advertise formal support or `real-device-verified`; multi-account UX remains deferred while internal keys stay account-scoped.
- Third-party SDK license metadata can be wrong or incomplete. Before adoption, inspect the repository license, package tarball license, transitive notices, maintenance activity, and security behavior. In particular, do not copy unlicensed community iLink clients or `UNLICENSED` QQ connectors; optional SDKs must remain lazy and non-mandatory.
- Control Core Step 1 (CC-1, 2026-08-25) now persists `hintTargets` per `(channel,userId,chatId)` and requires exact chat evidence before numbered question replies can decide. Wrong-chat and missing-chat messages are consumed fail-closed; legacy channel-level `hintChannels` rows are ignored for authorization. `notifyAll().delivered` remains channel-level only, so outbound broadcasts cannot prove a specific chat received the hint; channels without target-level `sendText` confirmation remain unable to use numbered fallback. Real-device/protocol validation of provider target delivery is still required.
- PR #12 modular QQ buttons/cards are contract-tested only. The implementation binds callbacks to `(channel,userId,chatId)` plus single-use token; C2C is single-chat, while GROUP, missing `chatType`, and unknown source metadata fail closed to avoid group-member disclosure. The conversation `routeUnsafe` bypass is blocked. `approval.parallel` is opt-in and disabled by default. Real QQ `INTERACTION_CREATE` payloads, keyboard permission behavior, callback ACKs, payload limits, and reconnect behavior still require device/protocol validation; do not mark `real-device-verified`.

## 2026-08-26 — local admin ask_user settlement entry (roadmap 阶段 2A)

- Web/admin now exposes a pending-question list and a protected settlement endpoint, but **only on the loopback-bound admin server**; there is still no safe desktop-side settlement entry, so dual-end sharing is not claimed.
- `GET /api/questions` and `POST /api/questions/:ref/settle` are gated by the admin Bearer token; settlement additionally requires a wired Control Core and a first-bound owner (`identity` + `ownerCount>=1`) in personal mode. If Control Core is unwired, settlement fails closed (`501` / `not_available`) with no direct-write bypass. All evidence is mock: no real host served a question to a phone, no real admin console clicked a button, no real settle round-trip was observed. Real-device validation sits on the handoff list.
- Ref is an irreversible 12-hex sha256 short form of the `aq:` key; admin event identity is bound to the question's precise `pushedTo` source target (never the operator), and settlement reuses the existing `question-answer` / `aq-skip` first-arrival semantics. Admin never fabricates a channel/chat and never authors ledger writes directly.
- Sanitized snapshots/audit/UI DOM must never carry token, credentials, full chat/user/agent identifiers, `pushedTo`, or answer privacy — this is pinned by focused tests (`test/admin-questions.test.mjs`, `test/questions-admin-settlement.test.mjs`, `test/admin-ui-behavior.test.mjs`). If an exposed field is ever added, the leak tests will fail and the panel must be re-audited before any release.

## 2026-08-26 — Stage 4 control-overlay persistence (session-registry + admin)

- The reviewed session control policy (`owner` / `approvalOwnerOnly` / `approvalMembers`) is now persisted as a bounded overlay at `route:sessions[<sessionId>].control`. A single pure `normalizeControlOverlay` (in `src/control/session-arbiter.mjs`) is the sole definition of a valid overlay and is shared by the registry, router, and admin write paths, so shape/bounds/rejections cannot drift. **Source fields are never allowed in the overlay**: `channel/accountId/userId/chatId/sessionId/policyVersion/expiresAt/revoked` are dropped on read and rejected (422) on write, so neither an admin payload nor a corrupted store edit can manufacture the source an authorization later compares against — fail-closed, constraint 2.
- Registry `getControl/clearControl` and router `setSessionControl` are data-plane only; the admin `PATCH /api/sessions/:id/control` validation side is strict (unknown/source/reserved fields, member triples with unknown inner keys, >64 members, >128-char owner/ids, wildcard/global, null-clear, missing session 404, storage failure 500). `GET /api/sessions` exposes only a **redacted** control summary (mode / approvalOwnerOnly / ownerConfigured / approvalMembersCount) — never raw identifiers — pinned by leak-free assertions. This is a persistence/API slice, **not** a second authorization system.
- **The persisted overlay is NOT yet wired into `createControlEntry` authorization.** There is no clean existing single-boundary Control Core policy-lookup hook (`createControlEntry` takes one static base policy), so wiring would require an invasive refactor of the just-reviewed source-binding hot path with regression risk to the round-2/3/4 adversarial fixes. This slice intentionally stays persistence/API-only; the exact next hook is documented in `.agents/workstreams/task-07-policy-persistence.md` (an optional `policyForSession` resolver merged into the base policy before the existing authorization checks — the overlay carries no source fields, so the reviewed source-binding logic stays authoritative). Until that wiring, setting an overlay changes what is **persisted**, not what authorizes a settle.
- Evidence is mock/contract only: no operator ever patched a real session overlay through the admin HTTP API, no host was restarted against a persisted overlay, no real provider callback ran against an overlay-backed policy, and `state.json` round-trip through the real file store is not exercised here. Contract-tested, not `real-device-verified`. Personal defaults remain safe because the overlay carries only the four approved fields and can never flip `converse`/`groupChatControl`.

## 2026-08-26 — team-mode approval membership contract

- Provider-neutral team approval scope routed through `src/control/entry.mjs` now resists event-manufactured owner sources: the merged-policy conversation binding is bound to the true original source (`rowMeta` → pending top-level → base policy) for `channel`/`accountId`/`chatId`/`sessionId`/`userId`, `owner` is never event-supplied, and owner/team-member settlement fails closed when no genuine conversation source exists. This closes the round-2 adversarial hole where a pending row omitting `accountId`/`channel` (e.g. `approvalOwnerOnly`/team owner) let the callback event mint the policy source the arbiter authorizes against. Legacy non-authorizing paths (action `stop`, conversation steering) keep adapter-envelope binding. Contract-tested only (`test/session-arbiter.test.mjs`, `test/control-entry.integration.test.mjs`): no real provider callback ever exercised a team member settle, and real QQ/Telegram/Feishu callback shapes at team scope are still unverified, so not `real-device-verified`.
- 2026-08-26 round 4 (conflict-consistency + legacy-envelope): `createControlEntry` now treats every present source authority — `basePolicy`, each of `pending.control`/`pending.controlMeta`, and the pending top-level — as a consistency constraint, so a stale/tampered `controlMeta` can no longer override a conflicting canonical base-policy channel/account: any disagreement among the layers (or with the event) for `approval`/`question-answer` fails closed (`source_mismatch_*`). Authorizing commands bind to the true original source unless an adapter `spec.authorize` proves the exact `pushedTo` target; they never fall back to event-supplied values. Non-authorizing `stop`/`steer`/`ordinary-message` keep an explicit legacy envelope binding (deterministic `pendingMeta` sessionId/key, event channel/account/user/chat) so legacy action/conversation rows with genuinely no source metadata still settle. Contract-tested only; real team-order provider callback shapes at team scope remain unverified, so not `real-device-verified`.
- Provider-neutral team approval scope is now explicit and bounded in `src/control/session-arbiter.mjs`: optional `approvalMembers` normalizes to capped (64) de-duplicated exact `(channel,accountId,userId)` triples, rejecting wildcard/global/empty/nested/unbounded input, and a pure `canSettleApproval(policy,event)` is wired into `canAcceptCommand`/Control Core only, covering both `approval` and `question-answer`. `approvalOwnerOnly=true` keeps owner-only; `mode='team'` with a non-empty list requires the exact triple unless the event is the owner; personal / team-without-list retain exact source binding; `steer`/`ordinary-message` are never granted by membership. Owner authorization (both `approvalOwnerOnly` and the team owner-exemption) is exact-source too: the event's `channel`/`accountId` must match the normalized policy channel/accountId in addition to the owner `userId`, so an owner id from the wrong channel/account can never settle (adversarial-repair commit). `src/control/entry.mjs` forwards the normalized policy snapshot to the settle callback. Evidence is mock/contract only (`test/session-arbiter.test.mjs`, `test/control-entry.integration.test.mjs`): no real provider callback ever exercised a team member settle, and the real QQ/Telegram/Feishu callback shapes at team scope are still unverified, so this is contract-tested, not `real-device-verified`.
- Persisting `approvalMembers`/`owner` through the session registry / loopback admin API is now landed (Stage 4, 2026-08-26) as a bounded overlay at `route:sessions[<id>].control` (see the Stage-4 risks section above) — but the persisted overlay is **not yet wired into needed `createControlEntry` authorization**, so no UI/adapter surface yet lets an operator configure a team member list that affects a live settle; the exact next hook is in `.agents/workstreams/task-07-policy-persistence.md`.
